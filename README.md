# 智驾中心交付物管理系统

一个面向智驾中心交付物治理的轻量级网页应用。系统采用 ASP.NET Core 10 单项目架构，同时承载前端静态页面、内部业务路由和 SQLite 数据库访问，用于集中维护交付物主档、版本生命周期、产品基线、变更闭环、交付物追溯关系及权限审计信息。

系统本身不存储大型交付物文件，实际软件包和文档继续保存在文件服务器；本系统负责记录文件位置、版本、元数据和业务关系，从而实现“文件存储与治理信息分离”。

## 当前功能

### 仪表盘

- 展示交付物总数、当前有效版本、待评审版本、本月变更等核心指标。
- 展示交付物类型分布、部门分布、月度新增/发布趋势和近期变更。
- 指标卡支持跳转至交付物台账、变更管理和完整度分析等业务页面。
- 统计口径在界面中提供说明，避免只展示数字而无法判断数据含义。

### 交付物台账

- 支持交付物查询、组合筛选、分页、详情查看和可选字段 CSV 导出。
- 交付物主档统一维护部门、类型、类别、项目/车型、责任人、私密等级、分享策略等元数据。
- 交付物编码由系统生成，规则为：`AD-部门编码-交付物类型编码-项目编码-交付物类别编码-三位流水号`。类别编码直接取自所选“交付物类别”的稳定字典编码，不单独保存重复的对象编码字段。
- 支持硬件软件包、PRD、FR、测试用例、测试报告等不同交付物类型，并为不同类型维护专属版本字段。
- 支持查看版本列表、版本详情、服务器文件路径及变更时间线。
- 尚未进入正式流程、全部版本均为草稿且没有变更、生命周期、关联关系或产品基线引用的交付物支持删除；删除行为写入审计日志。
- 正式业务数据采用归档而非直接删除，保留历史记录。

### 交付物类型与类别

系统采用两级分类模型：

```text
交付物类型
└─ 交付物类别
```

例如：

```text
硬件软件包
├─ 前视摄像头
├─ 周视摄像头
├─ 角雷达
├─ 激光雷达
├─ 毫米波雷达
├─ 超声波雷达
└─ 智驾域控制器

PRD / FR / 测试用例 / 测试报告
├─ 行车
├─ 泊车
└─ 主动安全
```

交付物类别不是前端固定枚举，而是统一基础数据。管理员可以在“基础设置”中按交付物类型维护类别编码、名称和排序。新增交付物、产品基线、筛选和完整度分析等功能统一读取同一类别数据源。

类别编码是稳定业务标识，同时作为交付物编码中的业务分类段。类别被交付物使用后，不允许修改所属类型或类别编码，但可以调整类别名称和排序；已被使用的类别不能直接删除。

### 产品基线

产品基线用于描述某一产品版本实际采用的硬件软件包组合及关联文档版本。

- 支持创建产品基线草稿，并维护产品名称、内部版本、适用车型、ODD、智驾能力和说明。
- 支持按交付物类别选择已发布/已替代的硬件软件包版本，并记录对应硬件型号。
- 支持关联 PRD、FR、测试用例、测试报告等正式交付物版本。
- 支持草稿编辑、正式发布、复制为新草稿和已发布基线的受控变更。
- 产品基线变更记录保存变更前后快照、原因、说明、操作人和时间。
- 只有 `DRAFT` 状态的产品基线允许删除；已经被其他基线引用的草稿不能删除。
- 产品基线的硬件类别直接来源于“基础设置 → 交付物类别”，不维护独立硬编码类别清单。

### 版本生命周期

版本生命周期用于管理单个交付物从草稿到正式发布、替代和废止的全过程。

主要状态包括：

```text
DRAFT（草稿）
→ IN_REVIEW（审批中）
→ READY_FOR_RELEASE（待发布）
→ RELEASED（已发布）
→ SUPERSEDED（已替代）
→ DEPRECATED（已废止）
```

核心规则：

- 首个版本从 `V1.0.0` 开始。
- 草稿版本提交后进入审批；审批通过只进入“待发布”，不会自动成为正式版本。
- 正式发布后成为当前有效版本，原当前版本自动进入已替代状态。
- 正式基线形成前允许继续按版本规则迭代；草稿或审批中阶段只允许存在一个开放版本周期。
- 正式基线形成后，正常修改必须通过变更流程创建变更版本。
- `VERSION_SUPPLEMENT`“补录版本”权限用于历史数据补录或特殊纠错，不作为正常版本修改入口。
- 支持退回修改、审批通过、正式发布和废止等动作，并记录生命周期操作信息。

## 版本号规则

内部版本号统一采用 `V主版本.次版本.修订号`：

| 版本类型 | 规则 | 示例 |
|---|---|---|
| 重大版本 | 主版本号 + 1，其他归零 | V1.2.3 → V2.0.0 |
| 功能版本 | 次版本号 + 1，修订号归零 | V1.2.3 → V1.3.0 |
| 修订版本 | 修订版本号 + 1 | V1.2.3 → V1.2.4 |

首个版本固定为 `V1.0.0`。后续用户只选择版本类型，系统根据该交付物现有合法版本自动计算下一版本号，并在提交时由后端再次校验，避免客户端直接指定非法版本号。

版本号用于公司内部统一管理；供应商/原始版本号作为独立字段保留，二者互不替代。

## 变更闭环

正式基线形成后，交付物的正常修改必须进入受控变更流程：

```text
发起变更（自动锁定当前正式版本）
→ 待评估
→ 批准 / 驳回
→ 开始实施
→ 创建并关联变更版本
→ 变更版本审批并正式发布
→ 提交验证
→ 确认关闭
```

系统不直接覆盖历史版本。变更后版本正式发布时会成为交付物当前有效版本，原当前版本自动标记为已替代。

变更管理支持记录变更类型、原因、内容、影响范围、关联问题、申请人、责任人、计划完成时间、评审人和评审意见等信息。批准、驳回、实施、创建变更版本、验证和关闭均使用独立权限控制。

仅尚未进入评审处理、状态仍为 `PENDING_ASSESSMENT` 且尚未创建变更版本的初始变更记录允许删除；进入后续流程后不允许直接删除。

## 交付物关联与追溯

交付物之间可以建立业务关系，用于表达需求、设计、验证及依赖链路。

支持关系类型：

- 派生（DERIVES）
- 验证（VERIFIES）
- 依赖（DEPENDS_ON）
- 引用（REFERENCES）
- 替代（REPLACES）

关联既可以建立在交付物级，也可以精确到具体版本。交付物详情页可查看上游/下游关系并跳转至关联对象。

完整度分析会利用这些关系计算 `PRD → FR`、`FR → 测试用例` 等追溯覆盖情况。

## 完整度分析

完整度分析用于从数据治理角度识别缺失项和追溯断点，包括：

- 交付物元数据完整度及部门维度完整度。
- PRD → FR 需求派生关系覆盖率。
- FR → 测试用例验证关系覆盖率。
- 各项目正式硬件软件包覆盖情况。
- 待审批版本、未关闭变更和长期未更新交付物等待处理事项。
- 数据问题清单，可直接跳转至具体交付物进行整改。

硬件覆盖标准不再固定为代码中的“7 类硬件”，而是实时读取“基础设置 → 交付物类别”中当前启用的硬件软件包类别。因此调整硬件分类后，统计口径会同步变化。

## 角色权限

系统已经从固定四角色模型升级为“**用户 → 角色 → 功能权限 + 数据范围**”的可配置权限体系。

### 功能权限

权限按业务模块拆分，例如：

- 交付物：查看、新增、编辑、归档、导出。
- 版本：查看、新增、补录、提交审批、退回、审批通过、正式发布、废止。
- 关联关系：查看、新增、删除。
- 产品基线：查看、新增、编辑草稿、发布、复制、变更。
- 变更管理：查看、发起、导出、批准、驳回、开始实施、创建变更版本、提交验证、关闭。
- 概览分析：仪表盘、完整度分析。
- 系统管理：基础数据、用户、角色权限、数据库备份和审计日志。

前端在操作入口按权限控制按钮可见性，后端仍执行最终权限校验，避免仅依赖前端隐藏实现安全控制。

### 数据范围

角色还可以按以下维度配置可访问数据范围：

```text
部门（DEPARTMENT）
项目/车型（PROJECT）
交付物类型（TYPE）
```

同一用户可以拥有多个角色，系统综合有效角色的功能权限和数据范围计算最终访问能力。

系统管理员角色拥有完整系统权限；其他角色可以根据实际岗位职责进行组合，不再局限于固定“编辑者/审批者/查看者”模型。

## 用户与账号安全

- 首次启动且没有用户时，通过初始化页面创建第一个管理员账号。
- Cookie 登录会话默认有效期为 8 小时，并支持滑动续期。
- 密码至少 8 位，同时包含字母和数字。
- 支持修改密码、管理员重置密码、账号启停和用户管理。
- 可要求新用户首次登录后强制修改密码；完成修改前不能访问其他内部业务接口。
- 已停用用户即使仍持有旧登录 Cookie，也会在后续请求中被强制退出。
- Data Protection 密钥持久化到 `data/keys`，避免程序重启后现有身份票据因临时密钥变化失效。

## 基础设置

基础设置负责维护全系统统一引用的主数据，目前包括：

- 项目/车型：项目编码、名称、车型、平台等信息。
- 交付物类型：定义 SWP、PRD、FR、TC、TR 等交付物类型及所属部门。
- 交付物类别：按交付物类型维护类别编码、名称和排序。
- 私密等级：公开、内部、秘密、机密。
- 对外分享策略：允许对外分享、审批后允许、禁止分享。

基础数据由交付物录入、产品基线、查询筛选和统计分析等模块统一引用，避免各业务页面维护重复枚举。

## 数据删除、归档与审计原则

系统区分“开发/录入阶段的无效草稿”和“已经进入正式业务链的数据”：

- 未形成有效业务关系的草稿允许物理删除，以便清理误录数据。
- 已进入审批、发布、变更、追溯或基线引用的数据原则上不能直接删除。
- 正式交付物退出使用时采用归档或版本废止，而不是删除历史记录。
- 草稿删除、生命周期动作、变更等关键操作均保留审计或业务记录。

这一规则用于兼顾日常录入体验和正式数据的可追溯性。

## 技术结构

```text
ASP.NET Core 10 单项目
├─ wwwroot/
│  ├─ index.html              单页应用入口
│  ├─ js/                     原生 JavaScript 业务模块
│  └─ css/                    页面及业务样式
├─ Controllers/               /internal/* 内部业务路由
├─ Services/                  SQLite访问、业务仓储、权限、备份等服务
├─ Security/                  Cookie认证、权限目录、授权中间件、密码服务
├─ Models/                    请求/响应及业务契约
├─ Data/schema.sql            数据表、索引及初始基础数据
├─ data/deliverables.db       运行后生成的 SQLite 数据库
├─ logs/                      运行时错误日志
└─ .github/workflows/         GitHub Actions 构建流程
```

前端采用原生 HTML / CSS / JavaScript，不依赖 Node.js、Vue、React 或在线 CDN。Node.js 仅在 GitHub Actions 中用于执行 `node --check` 前端 JavaScript 静态语法检查。

项目不启用 Swagger，也不规划将 `/internal/*` 作为公共 API；这些路由只服务于本系统网页和后端之间的内部交互。

SQLite 启用 Foreign Keys、WAL 和 busy timeout，用于本应用的轻量级本地数据持久化。

## 首次运行和升级

当前项目仍处于正式发布前开发阶段，数据库结构以当前 `Data/schema.sql` 为准。

首次运行时：

1. 系统初始化 SQLite 数据库和基础表结构。
2. 初始化权限目录和系统角色相关数据。
3. 如果数据库中没有用户，页面要求创建第一个管理员账号。
4. 密码至少 8 位，并同时包含字母和数字。
5. 管理员创建其他用户时，可以要求用户首次登录后修改密码。
6. 如果启用启动自动备份，程序启动后会生成 SQLite 在线备份并清理过期备份。

> 当前开发阶段的数据表调整不承诺兼容早期开发数据库。数据库结构发生破坏性变化时，开发测试环境可以删除旧 `data/deliverables.db` 后按最新 Schema 重新初始化。正式发布后的数据库升级策略需要另行固化。

## 开发运行

前提：开发电脑安装 .NET 10 SDK。

```bash
dotnet restore
dotnet run
```

默认访问：`http://localhost:5078`

推荐在提交代码前至少执行：

```bash
dotnet build -c Release
```

前端 JavaScript 可使用 Node.js 做静态语法检查：

```bash
node --check wwwroot/js/<file>.js
```

GitHub Actions 在合并至 `main` 的 Pull Request 和 `main` 分支 Push 时，会依次执行全部前端 JavaScript 语法检查、`.NET 10 Release build` 和 Windows x64 self-contained publish。

## 发布 Windows 64 位免运行时版本

双击：

```text
publish-win-x64.bat
```

或执行：

```bash
dotnet publish -c Release -r win-x64 --self-contained true \
  -p:PublishSingleFile=true \
  -p:IncludeNativeLibrariesForSelfExtract=true \
  -p:PublishTrimmed=false \
  -o publish/win-x64
```

发布目录中的程序包含 .NET 运行时。同事无需安装 .NET、SQLite、IIS、Node.js 或数据库软件。

GitHub Actions 成功执行后也会生成 `AdDeliverableManager-win-x64` Artifact，并保留构建产物 30 天。

## 运行模式

### 单机模式

保持 `appsettings.json`：

```json
"Application": {
  "AllowLanAccess": false
}
```

程序仅监听 `127.0.0.1`。双击 `AdDeliverableManager.exe` 或 `start.bat` 后，通过本机浏览器访问。

### 局域网共享模式

在指定运行主机上设置：

```json
"Application": {
  "AllowLanAccess": true
}
```

程序监听 `0.0.0.0`，其他同事通过以下地址访问：

```text
http://主机IP:5078
```

还需在 Windows 防火墙中允许对应 TCP 端口。默认端口为 `5078`，可以通过 `Application:Port` 调整。

SQLite 数据库必须保留在运行后端的电脑本地磁盘，不要把 `.db` 文件放到网络共享目录供多台电脑直接打开。

## 数据与文件

- 实际软件包、PRD、FR、测试用例、测试报告等文件继续存放在文件服务器。
- SQLite 只保存交付物元数据、版本信息、服务器路径、关联关系、变更、产品基线、账号、权限和审计信息。
- 文件路径可以在交付物版本详情中查看和复制。
- CSV 导出使用 UTF-8 BOM，可直接使用 Excel 打开。
- `data/*.db`、Data Protection 密钥、备份和日志不应提交到 Git。
- 未捕获的服务端异常写入 `logs/error-yyyyMM.log`，前端仅返回统一错误提示，详细异常保留在服务器日志。

## 分支管理模式

当前仓库长期分支包括 `main`、`dev`，日常开发使用主题分支。

建议统一采用以下分支模型：

```text
main                         正式稳定分支
└─ dev                       日常集成分支
   ├─ feature/<功能名称>      新功能开发
   ├─ fix/<问题名称>          缺陷修复和现有功能优化
   ├─ refactor/<模块名称>     不改变业务能力的结构重构
   └─ docs/<主题名称>         独立文档调整
```

### `main`

- 只保存经过验证、可以作为发布基线的稳定代码。
- 原则上不直接在 `main` 开发业务功能。
- 通过 Pull Request 合并时触发 Windows 构建与发布检查。
- `main` 的 Push 也会触发完整构建并生成 Windows x64 Artifact。

### `dev`

- 作为日常开发集成分支。
- 多个已经完成单独开发和基本自测的主题分支先合入 `dev` 进行集成验证。
- 当一个阶段的功能达到发布条件后，再由 `dev` 向 `main` 发起 Pull Request。

### 主题分支

新功能、修复、重构和独立文档工作应从最新 `dev` 创建主题分支，命名保持简洁并能表达工作范围，例如：

```text
feature/product-baseline
fix/version-permission
refactor/deliverable-workflow
docs/readme
```

同一个明确需求在一个主题分支持续迭代，不应因为同一需求中的连续修复或 UI 优化反复创建新分支。

主题分支完成后应：

1. 同步最新 `dev` 并解决冲突。
2. 完成本地/开发环境自测。
3. 提交 Pull Request 合并至 `dev`。
4. 集成验证通过后删除已经完成使命的短期主题分支。

紧急线上缺陷在系统正式发布后可增加 `hotfix/<问题名称>`，直接基于 `main` 修复；修复完成后必须同步回 `dev`，避免两个长期分支产生功能分叉。

### Commit Message

Commit 应描述一次清晰、可回溯的代码变化，推荐采用：

```text
feat: 新增交付物类别维护
fix: 修复变更审批权限判断
refactor: 收敛版本生命周期脚本
docs: 完善 README
style: 优化产品基线详情布局
chore: 调整构建配置
```

避免使用“修改一下”“update”“临时提交”等无法判断变更内容的描述。

> 分支管理的核心原则是：`main` 保持稳定、`dev` 负责集成、主题分支承载具体工作；分支数量服务于并行开发和风险隔离，而不是为了每一次小修改机械创建新分支。

## 当前边界

- 系统定位为智驾中心内部交付物治理工具，不是通用 PDM/PLM 或大型文档管理平台。
- 不在网页中上传、存储或下载大型交付物文件，只记录文件服务器路径和治理元数据。
- `/internal/*` 为内部业务路由，不作为第三方开放 API。
- SQLite 适合当前轻量部署方式；如果未来出现高并发、多服务实例或大规模数据访问，需要重新评估数据库架构。
- 产品基线当前聚焦智驾产品的软件包组合和关联正式文档，不替代整车级配置管理系统。
- 交付物类别由基础设置统一维护，硬件覆盖统计会随启用类别动态变化。
- 权限体系支持角色、功能权限及部门/项目/交付物类型数据范围，但不是独立 IAM 平台。
- 当前处于正式发布前开发阶段，数据库结构仍允许直接调整；正式发布前应冻结 Schema 基线并明确后续数据库升级策略。
