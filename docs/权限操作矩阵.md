# 权限操作矩阵

> 本矩阵基于 `fix/system-management-permission` 分支当前前端页面、按钮事件、Controller 路由、现有权限代码及数据库结构全量盘点形成。
> 本次重构以本矩阵为唯一业务授权基准：功能权限与审批权限统一为 Permission；数据权限仅保留部门、项目、交付类型。

## 一、权限模型

```text
用户 → 角色 → 功能权限
             └→ 数据权限
                 ├→ 部门
                 ├→ 项目
                 └→ 交付类型
```

- 系统内置 `SYSTEM_ADMIN / 系统管理员`：全部功能权限 + 部门/项目/交付类型全部数据范围。
- 自定义角色：默认无功能权限、无数据范围；按职责显式配置。
- 审批、驳回、实施、验证、发布、废止等均为普通功能权限，不再存在 Workflow Node 权限。
- 前端负责按钮显示/点击前检查；后端负责最终授权。

## 六、全局/非业务操作

以下属于登录用户自身操作或页面通用操作，不纳入角色功能权限：

- 修改当前登录用户自己的密码
- 退出登录
- 页面刷新
- 查询条件重置
- 分页
- 复制服务器路径
- 查看纯展示型详情（前提是拥有对应模块的 VIEW 权限）

## 七、数据权限规则

### 维度

仅允许：

- `DEPARTMENT`：部门
- `PROJECT`：项目
- `TYPE`：交付物类型

### 语义

- 每个维度显式配置 `ALL` 或一个/多个 `INCLUDE` 值。
- 自定义角色没有任何数据范围配置时：**没有业务数据访问权**。
- 系统管理员显式配置三个维度 `ALL`。
- 用户拥有多个角色时，以角色为授权上下文进行判断：某一角色必须同时满足该操作所需功能权限和该角色的数据范围；任一角色完整满足即可放行。禁止使用角色 A 的功能权限与角色 B 的数据范围拼接授权。
- 新建数据必须使用待创建对象的部门、项目、交付类型检查创建权限。
- 列表、详情、导出、变更、版本、关联及基线相关查询必须统一应用数据范围。
