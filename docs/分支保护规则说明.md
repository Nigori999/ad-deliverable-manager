# 分支保护规则说明

## 1. 文档目的

本文档说明 AD Deliverable Manager 当前 GitHub 分支保护策略、各规则的作用及典型使用场景，作为项目成员创建分支、提交 Pull Request（PR）和进行代码合并时的统一依据。

当前标准分支模型：

```text
main
  │
  └── dev
       ├── feature/*
       ├── fix/*
       └── hotfix/*
```

核心原则：

- `main`：正式发布分支，必须保持可发布状态。
- `dev`：开发集成分支，用于功能汇总、联调和集成测试。
- `feature/*`：新功能开发分支。
- `fix/*`：普通 Bug 修复分支。
- `hotfix/*`：生产环境紧急问题修复分支。

# 2. 分支保护总体架构

```text
                       ┌──────────────────────┐
                       │         main         │
                       │     正式发布分支      │
                       │        🔒 强保护      │
                       └──────────▲───────────┘
                                  │
                              PR / Merge
                                  │
                       ┌──────────┴───────────┐
                       │         dev          │
                       │     开发集成分支      │
                       │        🔒 保护        │
                       └───────▲──┬──▲────────┘
                               │  │  │
                    ┌──────────┘  │  └──────────┐
                    │             │             │
             feature/*         fix/*        其他开发分支
                    │             │
                    └────── PR ──┴─────────────┘

生产紧急修复：

main
 │
 └── hotfix/*
       │
       ├── PR → main
       └── 修复发布后同步 → dev
```

# 3. main 分支保护规则

## 3.1 保护目标

`main` 代表当前正式、可发布版本，因此禁止直接修改，只允许通过 PR 合并代码。

```text
main
├── ❌ 直接 Push
├── ❌ 直接 Commit
├── ❌ Force Push
├── ❌ 删除分支
└── ✅ PR → Merge
```

## 3.2 当前规则配置

| Rule | 当前建议 | 作用 |
|---|---:|---|
| Restrict creations | ❌ | 不限制分支创建 |
| Restrict updates | ❌ | 不使用额外 bypass 限制更新 |
| Restrict deletions | ✅ | 禁止删除 `main` |
| Require linear history | ❌ | 当前不强制线性历史 |
| Require deployments to succeed | ❌ | 当前未绑定部署环境 |
| Require signed commits | ❌ | 当前未要求签名提交 |
| Require a pull request before merging | ✅ | 禁止直接更新 `main`，所有变更必须通过 PR |
| Require status checks to pass | 暂不开 | 待 CI 构建/测试稳定后再启用 |
| Require code scanning results | ❌ | 当前不作为合并门禁 |
| Require code quality results | ❌ | 当前不作为合并门禁 |
| Restrict code coverage | ❌ | 当前不作为合并门禁 |
| Automatically request Copilot code review | ❌ | 当前不作为强制流程 |
| Block force pushes | ✅ | 禁止强制 Push，保护主分支历史 |

### Pull Request 子规则

| 子规则 | 当前建议 | 说明 |
|---|---:|---|
| Required approvals | `0` | 当前主要由项目负责人维护，避免单人开发时无法自审批 |
| Dismiss stale pull request approvals | ✅ | 新代码 Push 后使旧 Approval 失效 |
| Require review from specific teams | ❌ | 当前无需指定 Reviewer Team |
| Require review from Code Owners | ❌ | 当前尚未建立 CODEOWNERS |
| Require approval of the most recent reviewable push | ❌ | 当前主要为单人维护，暂不增加额外限制 |
| Require conversation resolution before merging | ✅ | PR 中所有 Review Conversation 必须解决后才能合并 |
| Merge commits | ❌ | 避免产生大量普通 Merge Commit |
| Squash and merge | ✅ | 一个功能/修复最终形成一个清晰提交 |
| Rebase and merge | ❌ | 当前不作为标准合并方式 |

> 团队进入多人正式协作阶段后，建议将 `Required approvals` 调整为 `1`，并考虑启用 `Require approval of the most recent reviewable push`。

# 4. main 规则的实际作用

## 示例一：直接 Push 被禁止

错误方式：

```text
git push origin main
        ↓
      ❌ 被规则阻止
```

正确方式：

```text
feature/xxx
    ↓
Push
    ↓
创建 PR
    ↓
Review / Checks
    ↓
Merge
    ↓
main
```

## 示例二：禁止 Force Push

即使执行：

```bash
git push --force origin main
```

也不能覆盖 `main` 的远程历史，避免误操作导致正式版本历史被重写。

## 示例三：Review Conversation 未解决

```text
PR
 ↓
Reviewer：DataScope 判断需要修改
 ↓
开发者修改代码
 ↓
Conversation 未解决
 ↓
❌ 不允许 Merge
```

完成修改并解决 Conversation 后，才可继续合并。

# 5. dev 分支保护规则

## 5.1 保护目标

`dev` 是开发集成分支，不代表正式发布版本，但承担多个功能分支的集成和测试职责。

```text
dev
├── ❌ 删除分支
├── ❌ Force Push
├── ✅ PR → Merge
└── 用于集成测试
```

## 5.2 当前规则配置

| Rule | 当前建议 | 作用 |
|---|---:|---|
| Restrict creations | ❌ | 不限制创建开发分支 |
| Restrict updates | ❌ | 不启用额外更新限制 |
| Restrict deletions | ✅ | 防止误删 `dev` |
| Require linear history | ❌ | 当前不强制线性历史 |
| Require deployments to succeed | ❌ | 当前不绑定部署环境 |
| Require signed commits | ❌ | 当前不强制提交签名 |
| Require a pull request before merging | ✅ | 功能分支进入 `dev` 通过 PR 集成 |
| Require status checks to pass | 暂不开 | 待 CI 稳定后再启用 |
| Require code scanning results | ❌ | 当前不作为门禁 |
| Require code quality results | ❌ | 当前不作为门禁 |
| Restrict code coverage | ❌ | 当前不作为门禁 |
| Automatically request Copilot code review | ❌ | 当前不强制 |
| Block force pushes | ✅ | 防止重写集成分支历史 |

### Pull Request 子规则

| 子规则 | 当前建议 | 说明 |
|---|---:|---|
| Required approvals | `0` | `dev` 以集成为主，当前不强制人工审批 |
| Dismiss stale pull request approvals | ❌ | 暂不增加集成阶段操作成本 |
| Require review from specific teams | ❌ | 当前无需指定团队 |
| Require review from Code Owners | ❌ | 当前尚未建立 CODEOWNERS |
| Require approval of the most recent reviewable push | ❌ | 当前不启用 |
| Require conversation resolution before merging | ✅ | PR 中的 Review Conversation 应解决后再集成 |
| Merge commits | ❌ | 保持提交历史简洁 |
| Squash and merge | ✅ | 推荐的标准合并方式 |
| Rebase and merge | ❌ | 当前不作为标准方式 |

# 6. dev 规则的实际作用

## 示例一：功能开发进入 dev

```text
feature/product-baseline
        ↓
开发 + 自测
        ↓
Push
        ↓
PR → dev
        ↓
集成测试
```

`dev` 作为共享集成区，不作为每个功能长期直接开发的工作区。

## 示例二：禁止删除 dev

```bash
git push origin --delete dev
```

该删除操作应被规则阻止。

## 示例三：禁止 Force Push

防止一个开发者错误 rebase / force push 覆盖其他成员已经进入 `dev` 的历史。

# 7. 标准开发与发布流程

## 7.1 新功能

```text
dev
 ↓
创建 feature/xxx
 ↓
开发
 ↓
自测
 ↓
PR → dev
 ↓
集成测试
 ↓
PR → main
 ↓
发布测试
 ↓
正式发布
```

## 7.2 普通 Bug

```text
dev
 ↓
创建 fix/xxx
 ↓
定位问题
 ↓
修复
 ↓
自测
 ↓
PR → dev
 ↓
回归测试
 ↓
PR → main
 ↓
发布
```

## 7.3 生产紧急问题

```text
main
 ↓
hotfix/xxx
 ↓
修复 + 验证
 ↓
PR → main
 ↓
发布
 ↓
同步修复到 dev
```

Hotfix 直接从 `main` 创建，以确保紧急修复基于当前正式版本；发布后必须同步回 `dev`，避免修复丢失。

---

# 8. 为什么采用这种保护架构

## main：发布质量门

`main` 保存当前正式、可构建、可发布版本，因此保护最严格。

## dev：集成质量门

`dev` 用于多个功能的统一集成、联调和回归测试，因此禁止删除和历史重写，同时要求代码通过 PR 进入。

## feature/fix：开发工作区

功能分支允许频繁 Commit，最终通过 Squash Merge 汇总为清晰提交进入集成分支。

# 9. 后续升级建议

## 阶段一：当前

```text
main
├── PR required
├── Delete blocked
├── Force Push blocked
├── Conversation resolution required
└── Approval = 0

dev
├── PR required
├── Delete blocked
├── Force Push blocked
├── Conversation resolution required
└── Approval = 0
```

## 阶段二：多人协作

建议对 `main` 增强：

```text
Required approvals = 1
Dismiss stale approvals
Require latest push approval
Conversation resolution
Squash merge
```

## 阶段三：CI/CD 完善

当 GitHub Actions 构建和自动测试稳定后，再启用：

```text
Require status checks to pass
```

形成：

```text
PR
 ↓
Build
 ↓
Automated Test
 ↓
Status Check Passed
 ↓
Code Review
 ↓
Merge
```

后续如果建立代码安全与质量体系，再考虑：

```text
Code Scanning
Code Quality
Code Coverage
CODEOWNERS
```

# 10. 成员操作速查

| 场景 | 从哪里创建 | 目标分支 | 是否 PR |
|---|---|---|---|
| 新功能 | `dev` | `dev` | ✅ |
| 普通 Bug | `dev` | `dev` | ✅ |
| 生产紧急 Bug | `main` | `main` | ✅ |
| 发布 | `dev` | `main` | ✅ |
| 日常开发 | `feature/*` / `fix/*` | - | - |

## 禁止操作

```text
❌ 直接 Push main
❌ 直接 Commit main
❌ Force Push main
❌ 删除 main
❌ Force Push dev
❌ 删除 dev
❌ feature/fix 直接合并 main
```

## 推荐操作

```text
✅ feature/* → dev
✅ fix/* → dev
✅ dev → main
✅ hotfix/* → main
✅ hotfix/* → main 后同步 dev
```

---

# 11. 一句话原则

```text
main 负责发布，必须严格保护；
dev 负责集成，保证持续可测试；
feature/fix 负责开发，允许快速迭代；
hotfix 负责生产救火，修复后必须回归 dev。
```
